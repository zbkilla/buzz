## Prerequisite fixes (droplet-specific)

1. **Docker Compose v2 required (>= 2.24.4).** Ubuntu's `docker-compose`
   1.29.2 (Python v1) cannot parse this bundle. `docker-compose-plugin` is not
   in Ubuntu repos; installed the plugin binary directly:

   ```bash
   mkdir -p /usr/local/lib/docker/cli-plugins
   curl -fsSL -o /usr/local/lib/docker/cli-plugins/docker-compose \
     https://github.com/docker/compose/releases/latest/download/docker-compose-linux-x86_64
   chmod +x /usr/local/lib/docker/cli-plugins/docker-compose
   docker compose version   # v5.3.1 at install time
   ```

2. **Docker iptables chains were broken.** First `./run.sh start` failed with
   `iptables ... DOCKER-FORWARD: No chain/target/match by that name` — the
   daemon's chains had been wiped after dockerd started (fail2ban/iptables
   reloads), and the running daemon (28.2.2) was stale vs the installed
   package (29.1.3). Fix, safe because zero containers were running:

   ```bash
   systemctl restart docker
   ```

   Restart rebuilds DOCKER-FORWARD and loads the current binary. Expect to
   need this again if iptables gets flushed while dockerd is up.

Non-default `.env` choices:

| Key | Value | Why |
|---|---|---|
| `BUZZ_HTTP_PORT` | `127.0.0.1:3000` | Compose interpolates to `127.0.0.1:3000:3000`, loopback-only publish. DOCKER-USER has no filtering and UFW is inactive on this box, so a bare `3000` would be open to the internet. |
| `BUZZ_DOMAIN` / `RELAY_URL` / media / CORS | `zbk-droplet.tail741ee0.ts.net` (`wss://` / `https://`) | Matches the tailscale serve front, so client-visible URLs are correct with no restart later. |
| `BUZZ_AUTO_MIGRATE` | `true` | Fresh DB; image embeds SQLx migrations. |

## Gotchas found during setup

- **Multi-tenant fail-closed Host binding.** The relay resolves a community
  from the request `Host` header before any WS/API handling. A request with
  `Host: 127.0.0.1:3000` gets a generic 404 ("no community is configured for
  this host"). Health (`/_liveness`) and NIP-11 work on any host; everything
  else must send the community host. The deployment community is auto-created
  at startup from the authority of `RELAY_URL` (`ensure_configured_community`
  in `crates/buzz-relay/src/main.rs`), and `RELAY_OWNER_PUBKEY` is
  auto-promoted to `owner` — no manual bootstrap needed for the first host.
- **Startup WARN noise is expected.** `transport drop ... if_match_race`
  warnings from `buzz_relay::api::git::store` are the git object-store A3
  conformance probe racing itself. Look for
  `git object-store backend admitted: A3 conformance probe passed`.
- **`generate-key` prints the secret to stdout.** Capture it in a script
  variable; a keypair echoed into a logged terminal is burned (one was, and
  was discarded).
- **README validation snippet** curls `/_liveness` on `BUZZ_HTTP_PORT`; with
  the `ip:port` form of `BUZZ_HTTP_PORT` that grep-based one-liner builds a
  malformed URL. Curl `http://127.0.0.1:3000/_liveness` directly.

## Operations

  recreate + backup reminder).

  tag once available; `./run.sh upgrade` to move.

  volumes live under `/var/lib/docker/volumes/buzz-prod_*`.

### Observing the agent from the terminal

`claude-agent-acp` drives a real Claude Code instance, so the agent's
sessions land in the standard session store
(`/root/.claude/projects/-root/<session-id>.jsonl`) alongside interactive
sessions. Identify agent sessions by their first user message: the harness's
`[Base] You are operating inside the Buzz platform ...` prompt. First
observed session: `8cfcdf3c-4982-47dd-b2de-cf7f6ee2fa2a` (2026-07-27).

Three views, in order of usefulness:

1. Full transcript in the Claude Code UI:
   `claude --resume <session-id>` (or bare `claude --resume` and pick it from
   the list). READ-ONLY by convention: the ACP adapter resumes this same
   session on every turn, so typing into it injects turns into the agent's
   context behind the harness's back.
2. Live turn/tool feed: `tail -f /root/.buzz/acp-claude.log` (equivalently
   `journalctl -u buzz-acp-claude -f`). The harness logs accepted mentions,
   turn lifecycle, and `tool_call: <title>` lines at info level, so mid-turn
   activity is visible before the reply posts.
3. Raw event stream: `tail -f /root/.claude/projects/-root/<session-id>.jsonl`.

Caveats:

- The session id is not a permanent handle — the harness may create fresh
  sessions (per channel, after resets). Stable observation points are the
  harness log and the `claude --resume` picker.
- lftui/Logfire does NOT see these sessions: telemetry only flows through
  the `claude-logfire` wrapper, and the adapter spawns Claude directly.
